## Recent results

- Runtime: generic call capture (`runtime/call_capture.c`, NEXT.md runtime target 1, first part).
  Off unless `BB_CALL_CAPTURE_DIR` is set, and then nothing changes for a name it does not wrap
  (`BB_CALL_CAPTURE_ONLY`; this filters call records only - `BB_CAPTURE_ONLY` is the case writer's
  separate filter, and the two share only the run id, `BB_CAPTURE_RUN`). When on, `bbgame_init`
  installs every hook through a recording thunk, and `pbboot` sends the trampoline of every import
  the runtime implements through one named `library.symbol`; imports bound to a bundled module's
  export are not wrapped (guest code there can return twice or unwind, which the thunk cannot carry).
  The thunk records the call's argument registers (rdi..r9, al, ymm0..ymm7) and return registers
  (rax, rdx, ymm0, ymm1, and st0/st1 when they hold a long double result), sampled like the old
  recorders (first 50 calls per name, then every 1000th, at most 200), as JSON lines in
  `$BB_CALL_CAPTURE_DIR/<name>/<run>.calls.jsonl`. It moves the caller's return address into a
  per-thread call frame so stack arguments stay where the caller put them, and finds the frame again
  through rbx and r12 (callee-saved), not by stack order.
  Hardened after an independent verification (branch `claude/verify-call-capture-r7k2qx`): longjmp
  out of wrapped calls, C++ exceptions thrown by host code through them (the thunk has unwind
  information), thread exit inside them, tail calls between them and recursion deeper than the old
  fixed 1024 frames all return to the right place; a call left without returning is noted (a
  warning per name, and a record with `"returns": null` if it was sampled) when the next wrapped
  call enters at its stack slot or the thread exits. Per thread, up to 2^20 wrapped calls can be in
  progress or left unnoted; past that, or out of memory, calls run unrecorded with a warning. A
  target that returns twice (setjmp) cannot be wrapped: its second return stops the process with a
  message. The thunk saves the x87 state around its record write.
  What it does not do: discover the memory a function reads (nothing is recorded behind a
  pointer), record stack arguments (their count is unknown without a signature), zmm upper halves
  or the x87/SSE control state. The records are not schema-1 cases and live outside the case
  library, so `tools/verify.py` and `tools/promote.py` do not read them; for most functions
  `tools/promote.py` still cannot move `edge-verified` to `verified` until the decisions below are
  made. Needs an AVX host (it saves whole ymm registers) that allows executable anonymous memory
  (the stubs are W^X, but under SELinux `deny_execmem` or similar the mapping still fails); without
  either it warns and wraps nothing. Signed off on the fork as an opt-in development facility
  (below): a call that returns on another thread now stops the run naming the call, every record is
  stamped with `record_format` and `capture_commit`, and `-DBB_ENABLE_CALL_CAPTURE=OFF` builds
  without it.
- Runtime: `sceKernelGetDirectMemorySize` (libkernel) is implemented. The console's direct memory
  region is 6 GiB - the public toolchain's `ORBIS_KERNEL_MAIN_DMEM_SIZE`, the console's 8 GiB of
  unified memory less the 2 GiB the kernel keeps - and the executable uses the result only as the
  search end of `sceKernelAllocateDirectMemory`. The boot now stops at that call instead
  (`eboot+0x2081aa3`, 116 MiB at 2 MiB alignment), which needs a direct-memory pool to hand out
  rather than one number, so it is queued as the memory manager in [NEXT.md](NEXT.md).
- Runtime: `scePthreadAttrGetaffinity` (libkernel) is implemented. An attribute reports the CPUs a
  PS4 application may run on - six of the APU's eight cores (mask `0x3f`) - so the game's own libc
  gets past its startup query: the boot reaches the `entry` milestone and stops at
  `sceKernelGetDirectMemorySize` (libkernel, called by eboot) instead.
- `BB_TARGET_FPS` (30, 60, uncapped) does what the community frame-rate patches "30 FPS++",
  "60 FPS++" and "Uncap FPS++" do, in every replaced function they edit, and each part is
  checked against the patch itself (`tools/verify.py run --patch FILE:NAME --env ...`,
  [VERIFY.md](docs/VERIFY.md)). Measured on a real screen (2026-10-07, 2560x1440 at 165 Hz, all
  replacements hooked, `BB_TARGET_FPS=60` with "60 FPS++"): frame pacing median 16.67 ms, p99
  16.69 ms, no frame over 1.5x the median.
- The runtime fork now starts native: no upscaler, no jitter, full screen at the display's size.
  With its temporal upscaler (FSR 3, jitter on), the sky showed the lower half of the screen
  mirrored into it; at native it does not.
- Unattended runs reach gameplay: `tools/play_route.py` plays `game/routes/*.route` (pad
  presses, keyboard text, waits on on-screen text): `new_game.route` goes from the title through
  character creation to the contract (which saves), `continue.route` loads that save into
  Iosefka's Clinic.
- Call counting probes (`BB_PROBES`, `runtime/probe.c`) show which original functions a run
  reaches; `tools/patch_overlap.py` and `tools/reloc_refs.py` map patches to functions and find
  callers through relocated pointers.
- Nine fixed-step state methods of a Chalice Dungeon state machine are replaced and checked on
  edge cases; they need a save that reaches the Chalice Dungeons to be recorded in-game.
- [QUIRKS.md](QUIRKS.md): Ghidra hides the code after calls to the engine's fatal error.
- The frame-rate patches also rewrite shared constants in the data segment (for example the
  1/30 s step at `0x04d29170`), which unreplaced code reads too. `BB_TARGET_FPS` is meant to run
  together with the patch for the rest of the game, so `verify.py run --patch` now applies the
  patch to both sides.

## Known issues

- Recording every hooked function at once slows frames enough to crash the runtime in the
  opening cutscene (a guest fault or a bad GPU command packet). With recording off, all
  replacements run clean; runs record only the functions they need (`BB_CAPTURE_ONLY`).
- An intermittent GPU library assertion (bad PM4 packet) while a save loads, about 75 s into a
  run, with or without recent hooks; the next run is clean.
- Rare NVIDIA Xid 32 errors at Vulkan device creation; the run aborts before game code runs.

## Decisions needed: generic capture (maintainer)

The call capture above stops where the case format starts. Schema 1, the harness's memory replay
and `tools/promote.py`'s contract are unchanged; `docs/capture-architecture.md` now describes the
call capture as built.

- **Fork decision: accepted as an opt-in development facility (2026-10-18).** Basis: the two
  independent verifications, `VERIFY-call-capture.md` (branch `claude/verify-call-capture-r7k2qx`,
  of `4c4c92c`: FAIL as written, D1 to D8) and `VERIFY-call-capture-hardening.md` (branch
  `claude/verify-capture-hardening-xb0hv6`, of `bad3066`: PASS, with N1 to N5), and the sign-off
  change on branch `runtime/generic-input-capture-signoff`, which meets the review's conditions:
  - N2: a wrapped call that returns on a different thread from the one it entered on stops the run
    with a message naming the call, and its record is dropped; the entering thread's identity is in
    every frame's serial and is checked before any bookkeeping is touched.
  - N1: top-level asm uses `.pushsection`/`.popsection`; `test_syslib` passes under gcc `-O0` with
    ASan and UBSan. CI's new `call capture` job runs the capture-on battery (`test_syslib`,
    `test_plugin`) at `-O0` under ASan and UBSan with gcc and clang (clang without
    `-fsanitize=function`, which reads a type signature before every indirect call's target and
    so faults on any generated stub).
  - Every record starts with `"record_format": 1` and `"capture_commit"` (the commit the capture
    code was built from, `-dirty` or `unknown` as it applies).
  - The stubs are W^X (code written once, then read-only and executable; data slots never
    executable).
  - `BB_ENABLE_CALL_CAPTURE` (CMake, on by default) compiles the thunk out entirely; CI checks that
    such a build has no thunk symbol. `BB_CALL_CAPTURE_DIR` remains the run-time switch, and with it
    unset the behaviour is the parent's.
- **Upstream decision: pending (D3).** Whether the trampoline goes to Yharnam-Hunters/Paleblood is
  the upstream maintainer's call. The commit depends on the fork's two syscall commits (`cf7a2c4`,
  `5376799`), which have to land upstream first (`VERIFY-call-capture.md`, Q6).
- **Fibers and context switching in the guest.** No: `symbols/imports.csv` (the executable and the
  two bundled modules) imports nothing from a fiber library (no `libSceFiber`, no `sceFiber*`) and no
  `getcontext`/`makecontext`/`swapcontext`. Its one context-related import is `libc.elf`'s
  `__Ux86_64_setcontext` from libkernel, by its name libunwind's primitive for resuming at an
  unwound frame (how an exception reaches its landing pad) on the same thread, not a switch between
  coroutines. Context switching
  written inside the executable itself would not show up as an import; none is known. So N2 has no
  known trigger in this game, and if one appears the run stops rather than going wrong.
- **Known gaps** (in the order of the harm they can do; `docs/capture-architecture.md`, "Known
  limitations", and the header):
  - Guest C++ exceptions cannot cross a wrapped frame: the guest unwinder finds no unwind
    information for the first host frame and calls `std::terminate`, a loud stop, never a silent
    skip (tested against the host unwinder; not confirmed against the target's own). No wrapped
    path crosses guest unwinding today.
  - A call returning on another thread stops the run (above).
  - A wrapped function that returns twice (setjmp-like) stops the process with a message; nothing
    wrapped today is one.
  - The frame is matched through rbx and r12; a target that breaks the System V rule stops the
    process or, with a stale value, could crash. A target that overwrites its own return-address
    slot, or switches stacks and reuses one slot for a still-running call, breaks the "same slot
    means the earlier call was left" rule.
  - A signal handler on the same thread that makes a wrapped call while the thunk is in its enter
    or leave helper can corrupt that thread's frames (no signal masking).
  - The stubs need executable anonymous memory; a host that refuses it wraps nothing, with a
    warning.
  - Only ymm0..ymm7 are saved (no AVX-512 upper halves); left calls are noted late; frame memory is
    kept for the life of the process; the per-call cost is about twice the first version's.
  - Untested: the no-AVX fallback and a refused stub mapping (both warn and wrap nothing).
- **Return class.** A record holds rax, rdx, ymm0 and ymm1, but `rt_hook_entry` carries no
  signature, so a record cannot say which of them is the result, and a case's `returns` cannot be
  filled honestly from it. Proposal: take the return class from the function's edge cases, which
  already state it (`returns` in `game/<system>/*_cases.py` output), keyed by hook name; a function
  without edge cases stays unconvertible.
- **Memory.** No memory a function reads is discovered. The old recorders rewrote pointers in
  recorded memory by hand (`buf:`/`guest:`); generic capture would need either per-function
  descriptors or memory replay at the original host addresses. Which one is a case-format decision.
- **Conversion.** No tool turns call records into cases; one would need both decisions above.

## Open questions (runtime)

- `scePthreadAttrGetaffinity` reports the six-core application CPU set (mask `0x3f`), taken from the
  PS4's documented core split - two of the APU's eight cores are reserved for the system, six are
  left to applications (PS4 Developer wiki, "APU"; Naughty Dog on the console's CPU) - and a shipped
  PS4 title's spelling of "all cores" as 63. What public evidence does not settle: that the
  system-created main thread's default mask is exactly this whole set rather than a subset of it,
  and the target result and error for a mask that names no core (`scePthreadAttrSetaffinity`, still
  unimplemented and a named diagnostic). A console measurement, or a guest call site that sets a
  strict subset, would close it.
- `sceKernelGetDirectMemorySize` returns the console's documented direct memory region, 6 GiB (`docs/runtime-syscalls.md`, "Direct memory size"). What stays open is the number a console answers a *particular title*: public console logs give the application's share per memory mode (BigApp memory 5248 MiB on a base console, 5888 MiB on a PS4 Pro) and one shipped title expects a share of its own (`0x15f200000`) and halts on anything else. Bloodborne's four call sites only bound an allocation with the value, so the choice cannot change what the boot does; a console measurement of the call would close it.
